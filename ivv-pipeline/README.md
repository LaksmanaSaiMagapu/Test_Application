# IV&V Pipeline on OpenHands — operator guide

Drives the four IV&V agents through the OpenHands Agent Server REST API.
Matches the reference architecture in `../openhands-airgapped-ivv.html`
(pipeline stages 2, 3, 5, 6).

## Layout

```
profiles/           LLM profiles (volume=gemma, reasoning=nemotron) — registered via API
agent-profiles/     IV&V agent personas (system-prompt rules per stage)
prompts/            Stage prompt templates with {{VAR}} placeholders
automations/        Automation-service definitions (webhook/cron triggers)
dispatch.py         CLI: setup / run / list / evidence  (pure stdlib)
evidence/           Downloaded trajectories land here (created on first run)
```

## Quick start (local Docker instance)

```bash
cp .env.example .env          # set LLM_BASE_URL + LLM_API_KEY (your endpoint)
python3 dispatch.py setup     # registers LLM + agent profiles into Agent Server

# smoke test against the sample GIS playground
python3 dispatch.py run \
  --profile ivv-unit-test-writer \
  --prompt prompts/unit-tests.md \
  --workspace /projects/gis-sample \
  --var REPO_PATH=/projects/gis-sample \
  --var MR_IID=1 --var MR_SHA=HEAD --var TARGET_BRANCH=main \
  --tag smoke-test

python3 dispatch.py list
python3 dispatch.py evidence <conversation_id>
```

Then open http://localhost:8000/canvas — the conversation appears with its
tags; watch the agent work live, review its diff, approve or discard.

## The four agents

| Profile | LLM tier | Pipeline stage | Output |
|---|---|---|---|
| `ivv-unit-test-writer` | volume (gemma) | 2 · MR unit tests | test files + TEST-INTENT table + suspected defects |
| `ivv-sonar-remediator` | reasoning (200B) | 3 · static analysis gate | minimal fix branch + issue table |
| `ivv-e2e-author` | reasoning (200B) | 5 · nightly E2E | Playwright specs + reports + traces |
| `ivv-defect-triager` | reasoning (200B) | 6 · failure triage | tracker-ready defect tickets |

Guardrails are encoded in each agent profile's `system_prompt_suffix`
(read-only vs fix-allowed, evidence requirements, naming/traceability rules)
— not just in prompts, so they hold across all runs.

## From manual dispatch to automation

`automations/*.json` is the target-state wiring for the OpenHands Automation
service (FastAPI + PostgreSQL, cron + webhooks). In the airgapped deployment:
1. Import the three definitions via the automation service API.
2. Point GitLab/Gitea webhooks at the automation service's webhook endpoint.
3. The dispatcher inside the automation service does what `dispatch.py run`
   does here — plus run-history persistence (the audit trail).

Until then (and for local familiarization) `dispatch.py` plays the same role
manually. The template vars in `automations/*.json` (`{{object_attributes.iid}}`
etc.) follow GitLab webhook payload paths.

## Airgap notes

- Everything calls only `AGENT_SERVER_URL` and `LLM_BASE_URL` — both internal.
- `dispatch.py` reads the session key from `.openhands/agent-canvas/api-key.txt`
  (auto-generated by agent-canvas) or `SESSION_API_KEY` in `.env`.
- Keep `evidence/` under your evidence-retention policy; trajectories are the
  machine-readable record of what the agent did and why.
